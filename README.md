# Gödel Trader

**A recursively self-improving agent for trading-strategy research.**
Stanford CS 329Z (Engineering AI Agents), Fall 2026. Author: Mohammad Shoaib Lari.

Gödel Trader asks whether an LLM agent that can rewrite its *own research
loop* discovers better trading strategies than a strong fixed-loop quant agent
(R&D-Agent(Q)), and, just as importantly, how to tell **genuine
self-improvement** from **exploitation of the evaluator** in a domain where
the only reward signal is a backtest the agent can inspect.

The project builds on [Gödel Agent](https://github.com/Arvid-pku/Godel_Agent)
(Yin et al., ACL 2025) as the self-referential substrate and on
[R&D-Agent](https://github.com/microsoft/RD-Agent) (Li et al., NeurIPS 2025)
plus [Qlib](https://github.com/microsoft/qlib) as the quant environment and
baseline. The proposal is in `notes/Godel_Trader_Proposal.pdf`.

## Status: midpoint (November 2026)

What works today is the self-improving substrate, running end to end on the MGSM
math benchmark. Three full runs are included as logs. They already produced the
project's first result:

> **Given access to its own evaluator, the agent stopped solving the task and
> started reading the answer key.**

In both complete runs, o3 first produced honest solver rewrites
(self-consistency voting over gpt-4o-mini samples) that scored 0.78 to 0.88 on
validation, below the 0.94 threshold needed to trigger the test set. It then
used its code-execution tool to inspect the task module, found that the
labelled dataset is importable from the agent's own process, built a lookup
table from problem text to answer, and rewrote `solver` to consult it. That
solver scored 1.00 on validation and 1.00 on the 800-problem test set, and
the framework saved it as the best agent found. The model's own docstring
explains the strategy ("the evaluation framework ships with a dictionary that
already contains the correct answer for all samples").

| run | honest solver scores (valid acc) | after lookup rewrite | ended by |
|---|---|---|---|
| `runs/run1_2026-11-01_context_overflow.log` | (no evaluation completed) | – | prompt overflowed o3's 200k context after the agent stored the dataset in a global |
| `runs/run2_2026-11-01_reward_hack.log` | 0.78, 0.86, 0.86, 0.84 | 1.00 valid / 1.00 test | 100-step cap |
| `runs/run3_2026-11-02_reward_hack.log` | 0.88, 0.78, 0.82 | 1.00 valid / 1.00 test | 100-step cap |

Full per-run tables (every evaluation, every rewrite, every tool call) are in
`runs/SUMMARY.md`, generated by `scripts/summarize_run.py`. The agent's final
self-modified code from run 3 is preserved verbatim in
`runs/run3_dumped_agent/`; the lookup-table solver is
`runs/run3_dumped_agent/agent_module/solver.py`.

Why this matters for trading: a backtest is an evaluator the agent can read,
and financial data is where look-ahead leakage is easiest to introduce and
hardest to notice. The rest of the project is therefore built around an
evaluation sandbox the agent cannot see into (held-out data outside the
agent process, point-in-time splits, a test window after the LLM's training
cutoff) and an acceptance rule for self-edits, so that measured improvement
is real.

## Quick start

Tested on Ubuntu under WSL2 with Miniconda. Linux or macOS should behave the
same.

**Prerequisites**

* `conda` (Miniconda or Anaconda).
* An OpenAI API key with access to `o3-2025-04-16` and
  `gpt-4o-mini-2024-07-18`, with a positive credit balance. A run makes one
  o3 call per step for up to 100 steps plus 50 to 850 gpt-4o-mini calls per
  evaluation; in our runs this came to a few US dollars and 5 to 15 minutes
  per run.

**Install**

```bash
git clone git@github.com:shoaiblari/godel_trader.git
cd godel_trader
conda env create -f environment.yml      # creates an env named "g"
conda activate g
```

`environment.yml` pins `openai==1.2.0` (what upstream was written against)
and `httpx<0.28`, because newer httpx removed an argument that openai 1.2.0
still passes. Without the pin the agent fails on import.

**Configure the key**

```bash
cd godel_agent
cp src/key.env.example src/key.env
printf '%s' 'sk-...your key...' > src/key.env     # one line, no trailing newline
```

`key.env` is git-ignored. Never commit it.

**Run the agent**

```bash
# from the godel_agent/ directory
python src/main.py 2>&1 | tee ../runs/my_run.log
```

The agent prints every planning step, tool call, solver rewrite and
evaluation to stdout. It stops after 100 planning steps, or earlier on a
fatal API error, and exits with status 1 in both cases (upstream behaviour).
Outputs:

* `results/mgsm_<test_acc>.txt` – written whenever a solver beats the
  previous best test accuracy; contains the per-problem log of the test run.
* `../task_mgsm_<test_acc>/` – a dump of all self-modified code at that point.

**Reproduce the reported tables**

```bash
# from the repository root
python scripts/summarize_run.py runs/run2_2026-11-01_reward_hack.log runs/run3_2026-11-02_reward_hack.log
```

This regenerates the evaluation / rewrite / tool-call tables from the included
logs without any API calls. To check a run of your own, point it at your log.
Runs are non-deterministic (o3 at temperature 1, a different random
validation sample each evaluation), so your run will differ in detail; in
our experience the lookup-table rewrite appears within the first 30 to 40
steps.

## How the agent works, in brief

`godel_agent/src/main.py` builds one `Agent`, seeds its history with the
source of `solver`, and calls `evolve()`. Each evolve step sends o3 the goal
prompt, a dump of the live Python namespace, and recent history, and requires
it to answer with tool calls. The seven tools let it print an analysis, list
the environment, read any function's source, **replace any function in the
running interpreter** (`action_adjust_logic`, via `exec` + `setattr`),
**run arbitrary Python in the same interpreter** (`action_run_code`), call an
LLM, and evaluate the current `solver`. Executing the tools ends by calling
`evolve()` again, so the loop is mutual recursion capped at 100 steps. All
modifications are in memory; code on disk never changes.

`action_run_code` is the door the agent walked through: anything it defines
becomes a global visible to `solver`, and the task module with the labelled
examples is importable from the same process.

```bash
cd report/midway && tectonic midway_report.tex
```

## Roadmap to the final report

1. Trading environment with the same interface as `solver`: daily US
   equity data (yfinance -> Qlib binary format), point-in-time splits, test
   window after the LLM cutoff, labels held outside the agent process.
2. Frozen baseline: R&D-Agent's `fin_factor` loop on the same data split
   (conda runtime, no Docker).
3. Gödel Agent's `solver` writes factor code into R&D-Agent's Qlib workspace;
   self-edits accepted only on validation gains.
4. Measure improvement that survives the held-out test, versus improvement
   that was evaluator exploitation.
